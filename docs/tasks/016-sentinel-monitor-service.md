# 016: Sentinel Monitor session logic (Rust)

## Goal

Make risk-sentinel's `Monitor` stream do its job:

- decode execution reports into fills;
- run the risk engine;
- send risk commands downstream with unique ids;
- track acknowledgements;
- ignore duplicate reports after reconnects;
- keep the session alive with heartbeats.

## Context

- `rust/crates/risk-sentinel/src/service.rs`:
  - `Sentinel` implements `RiskSentinelService`;
  - the handshake (`expect_hello`, `SessionAccept`) works and is tested in
    `tests/monitor_handshake.rs`;
  - `handle_upstream` ignores `Execution` messages (`TODO(task-016)`).
- Task 015 provides `RiskEngine::on_fill → Vec<RiskAction>`.
- [ADR-0013](../adr/0013-risk-feedback-loop.md):
  - `command_id` is the idempotency key;
  - exchange-core acknowledges with `CommandApplied` once all shards applied
    a command;
  - reports may repeat after a reconnect. Deduplicate by
    `(shard_id, shard_sequence, is_maker)`: one trade yields a maker and a
    taker report with the same `(shard_id, shard_sequence)`.
- Proto types: `lockstep_proto::v1::*` (generated by the `lockstep-proto`
  crate from `/proto`).

## Interfaces to implement

- Extract session handling from `service.rs` into `session.rs`:

  ```rust
  pub struct Session { /* engine handle, dedup state, pending commands */ }
  impl Session {
      /// Pure-ish: returns the downstream messages to send for one upstream message.
      pub async fn handle(&mut self, message: MonitorRequest) -> Vec<MonitorResponse>;
  }
  ```
- **Decoding:** `ExecutionReport` → `engine::Fill`. Reject an unknown `Side`
  by logging and skipping, never panicking.
- **Command ids:** a monotonically increasing `u64` per sentinel process,
  starting at 1.
- **Pending commands:** a map from `command_id` to
  `(RiskAction, sent_at: Instant)`. On `CommandApplied`, remove the entry and
  log the latency. Commands unacknowledged after 5 s are logged as warnings;
  they are not resent, since the exchange journals and applies what it
  received.
- **Duplicate detection:** a bounded set (for example the last 1 000 000
  keys, FIFO eviction) keyed by `(shard_id, shard_sequence, is_maker)`.
- **Heartbeats:** send one downstream every 1 s. Close the session if no
  upstream message arrives within 5 s.
- **CLI flags** in `main.rs` for the three limits (defaults from
  `RiskLimits::default()`).

## Acceptance criteria

1. **Unit tests on `Session::handle`** (no network):
   - a breaching report yields exactly one `RiskCommand` with id 1;
   - the next breach from another trader yields id 2;
   - a duplicate report yields nothing;
   - `CommandApplied` clears the pending entry.
2. **Integration test** (`tests/monitor_session.rs`, loopback like
   `monitor_handshake.rs`): a client sends hello and then reports that
   breach `max_abs_position`. It receives `SessionAccept`, then a
   `RiskCommand::BlockTrader` for the right trader.
3. The existing handshake tests still pass.
4. `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and
   `cargo test` pass.
